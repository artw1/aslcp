# Handover notes

Read this first in a new session, then `docs/DESIGN.md`, `docs/API.md` and `CHANGELOG.md`.

## What ASLCP is

A web control panel for AllStarLink 3 nodes (Debian 12 or 13 / Raspberry Pi OS, arm64/armhf/amd64): an AllScan replacement (live status, connect/monitor, favorites, lookup), a public read-only status page, and (next) configuration editing. Tested on ASL3 (Asterisk 22) on Raspberry Pi hardware.

## Repository (single public repo)

- **`artw1/aslcp`** holds everything: the source on `main` (README, LICENSE, SECURITY.md, issue forms in `.github/ISSUE_TEMPLATE`, screenshots in `docs/images`), the GitHub releases (created from the `vX.Y.Z` tags) and the signed apt repository on the **`gh-pages`** branch (`pool/`, `dists/`, `latest.json`, `latest-beta.json`, `install.sh`, keyring files, `index.html`). GitHub Pages serves `gh-pages` (root) at https://artw1.github.io/aslcp, so the apt URL is `APT_URL` in the Makefile and workflows.
- `gh-pages` is written only by the workflows (`release.yml`, `promote.yml`, `apt-remove.yml`) through `packaging/apt-checkout.sh` and `packaging/publish-apt.sh`, using the built-in `github.token` (`permissions: contents: write`); there is no personal access token. Never edit or push `gh-pages` by hand.
- Development sessions may be configured with a `claude/*` branch; the maintainer has said to push directly to `main`. Check `git remote get-url origin` before any git network command.
- Because the repository is public, never commit secrets, real IPs or other operators' callsigns.

### One-time setup (maintainer)

1. Create the public repository `artw1/aslcp` (empty) and push the source to `main`.
2. Add the repository secret `APT_SIGNING_KEY` (Settings > Secrets and variables > Actions): the armored private GPG key that signs the apt repository (uid "ASLCP apt repository", RSA 4096, no passphrase). It replaced the earlier key when the repository was recreated at 1.1.20; nodes installed before that need the new public key once (`sudo curl -fsSL -o /usr/share/keyrings/aslcp-archive-keyring.gpg https://artw1.github.io/aslcp/aslcp-archive-keyring.gpg`). GitHub secrets cannot be read back; the maintainer keeps a copy of the key.
3. Settings > Actions > General > Workflow permissions: the workflows request `contents: write` themselves, but "Read and write permissions" must not be blocked by an organization policy.
4. Push the first tag `vX.Y.Z`. The Release workflow creates the orphan `gh-pages` branch on this first run (and the pre-release).
5. After that first release: Settings > Pages > Build and deployment > Source "Deploy from a branch", branch `gh-pages`, folder `/ (root)`. Then check https://artw1.github.io/aslcp/ and `install.sh`. (Until the branch exists it cannot be selected.)

## Releasing

Versions are plain `X.Y.Z`. Stable is 1.0.0 (branch `release/1.0`); `main` carries 1.1.x. Every tag is first a beta; a release is a separate **promote** step. (1.1.1 to 1.1.15 were published as 2.0.0-beta.1 to 15, and those packages were removed from the apt repo.)

1. Add a `## [X.Y.Z]` section to `CHANGELOG.md` on the branch being released (the release notes come from it), push to `main`, wait for CI.
2. The maintainer pushes the tag `vX.Y.Z` (or creates it on https://github.com/artw1/aslcp/releases/new, target `main`, "pre-release" ticked). Tag pushes from development sessions are blocked; do not work around that (the maintainer chose to keep the final say). Only tags of the form `vX.Y.Z` trigger the build.
3. `.github/workflows/release.yml` (taken from the tagged commit) tests and builds the three debs, then `packaging/publish-apt.sh` puts them in `pool/beta`, writes `latest-beta.json`, signs (secret `APT_SIGNING_KEY`) and pushes to the `gh-pages` branch of this repository (built-in token); the debs are attached to a GitHub pre-release. Suite `beta` indexes all of `pool/`, suite `stable` only `pool/main`. `install.sh` is refreshed only when the published version is the newest in the pool. The newest 5 builds per architecture are kept in each pool directory (the version just added is never pruned).
4. After testing on a node (Updates > Beta), the maintainer runs the **Promote** workflow (Actions > Promote > Run workflow, input `version`, e.g. `1.1.16`, no leading v). It moves exactly those debs from `pool/beta` to `pool/main` (no rebuild), regenerates and signs both suites, updates `latest.json`, and marks the GitHub release as a full release (and "latest" if it is the newest stable version). It refuses a version that is not in the beta suite and is safe to run twice. If the release has deb assets they must be identical to the packages in the apt repo.
5. Nodes update from the Updates tab or `apt upgrade`; the channel (Release/Beta on the Updates tab) is the suite word in `/etc/apt/sources.list.d/aslcp.list`, switched by the helper ops `update-channel-stable|beta`.
6. To delete unwanted beta packages: the **Remove from beta** workflow (`.github/workflows/apt-remove.yml`; inputs `glob`, `keep_version`, `apply`; dry run unless `apply` is ticked; it only touches the beta pool and refuses if `keep_version` would be gone). It runs `publish-apt.sh --remove`.
7. To delete old GitHub releases (for example `v2.0.0-beta.*`, whose tags are already gone): the **Delete releases** workflow (`.github/workflows/release-delete.yml`; inputs `glob`, `delete_tags`, `apply`; dry run unless `apply` is ticked). It deletes matching pre-releases by release id (never full releases); with `delete_tags` also the matching git tags, except a full release's tag. It does not touch the apt repository.

**Backports:** fix on `main`, then `git cherry-pick -x <sha>` onto `release/1.0`, add a `## [1.0.N]` changelog section there, push the branch (`git push origin release/1.0`), maintainer tags `v1.0.N` on `release/1.0`. The same rule applies: the build goes to beta (older than the current beta, so nobody on beta is offered it) and the maintainer promotes `1.0.N` to reach stable. Promoting an older version never changes `latest.json` while a newer stable exists. Fixes found only in 1.0 go to `release/1.0` and are forward-ported to `main`.

## Working agreements

- `CLAUDE.md`: launch subagents for each task and use the cheapest adequate model. Use Haiku for small, well-defined jobs (doc edits, small fixes, version bumps) and Sonnet for multi-file features; review security-relevant work carefully, lighter review for low-risk changes.
- The repository is public. Bug reports go to its issues; security reports via GitHub private vulnerability reporting.
- A real node's `/etc/asterisk` and AMI captures were used for testing; only anonymized excerpts are committed. Never commit real secrets, IPs or other operators' callsigns.
- Design preferences from the maintainer: dark theme default; AllScan-like density (status table at top with red = TX / keyed link, green = local RX, then the connect bar with "Disconnect before Connect" on and "Disconnect before Monitor" off, then a favorites table; network list always open); no PHP; easy install/update; one port with public view + login.
- app_rpt has a single command slot per node: commands to one node must be spaced (rpt.Client.MinGap) and an exclusive connect waits for dropped links to disappear.

## Experiments (try/* branches)

To try an idea on one node without a release: push it to a branch `try/<name>`. CI builds the debs and attaches them to the run as the artifact `debs-try-<name>-<version>` (kept 14 days); nothing goes to the apt repository or GitHub releases. Untagged builds are versioned `X.Y.Z+dev.N.g<sha>` (N commits after the last release tag `vX.Y.Z`), which sorts above X.Y.Z and below the next release, so the next real release installs over it. Install on the node with `sudo apt install ./aslcp_<version>_<arch>.deb`; go back with `sudo apt install --allow-downgrades aslcp=<release>`. If an experiment changes the database or config format, say so: going back may need care. Keep or drop: merge the branch to `main` (it then ships in the next release) or delete it.

Parked and running experiments, with their status and how to resume: `docs/EXPERIMENTS.md`.
